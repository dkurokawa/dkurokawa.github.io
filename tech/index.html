AI 駆動開発

使い分けと、手放さない範囲

設計は自分が 7 割、実装は生成とレビューに寄せ、検証は協働。この配分に落ち着きました。 設計を投げると崩れ、実装を全部自分で書くと遅い。 AI が書いたコードは自分で読んで採否を決めています。

  • 業務用語をコードの行番号と 1:1 で紐付けた用語集をモデルに読ませ、型の取り違えを止めた
  • 開発フローの各段（PR 作成・実装・QA 依頼・green/blue デプロイ）を自作のスキルとして 15 本用意し、issue 番号を渡すと進む形に。進捗は機械可読の JSON
  • PR の差分と issue の完了条件を突き合わせて、動作確認シートを HTML で自動生成。確認する URL も自動で並ぶ
  • 過去 10 ヶ月分の issue・PR・レビューコメント・差分に現行ソースを加えて意味検索する RAG を自作。実装前に決定の経緯を引き、grep より先に当たりを付ける
  • 追跡の運用負担が週 2〜3 時間から 15 分に

paper-pipeline 稼働中

6 段パイプライン / メダリオン構成のデータレイク

大量のドキュメントを自動収集し、要素分解して段階的に構造化・検証・合成する文書処理基盤です。

  • AI 推論の 4 段すべてを自宅のローカル LLM で完結。外部 API のコストはゼロ
  • データレイクは bronze（生）→ silver（構造化）→ gold（配信できる形）の 3 層を自分で設計・実装
  • 層の実体は R2、処理の進行は PostgreSQL のステートマシン。データと進行を分離
  • 取り込み時に関連文書をまとめて LLM に渡し、合意点・矛盾・空白を合成（バッチの RAG）。クエリ時の生成は下流に分けています
  • 出口は埋め込みベースの検索 API。常駐ワーカー 9 本と watchdog で運用

車両インパネの2段ハイブリッド推論

ブラウザ ONNX + サーバ GPU / 業務の空き時間に個人的に進めた取り組み

車両の計器盤画像から状態を判定する推論を、2 段構成で組みました。

  • ブラウザ上の ONNX（YOLOv8・5.8MB）で一次判定し、判断がつかない画像だけサーバの GPU で本推論
  • 全部を GPU に投げる構成に比べ、処理を大きく削れる
  • 検証データ 882 枚で精度 95.0%（混同行列つき）。ar_id 単位の 5-fold で測り直しても 94.9%（±2.4）
  • スマホで動くところまで作りましたが、本番には乗っていません
